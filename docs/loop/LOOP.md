# ループ手順書

毎日 **0:00 JST** に AI が自律実行する手順。AI はこのファイルを読んでその通りに動く。
人間が読む場合は「今晩何が起きるか」の説明書として読める。

```
 ①調査 ─▶ ②取り込み ─▶ ③仕様更新 ─▶ ④計画 ─▶ ⑤実装 ─▶ ⑥検証 ─▶ ⑦レビュー ─▶ ⑧記録
 最新情報  フィードバック   specs 反映   1〜3件選ぶ   TDD     test+lint   AIが独立監査   journal
                                                                              │
                                                                         main へ push
```

所要の目安: 1 回 30〜60 分。**終わらないときは途中で止めて記録する**（積み残しは次回へ）。

> **成果物は人間のレビューを待たずに `main` へ入る**（2026-08-15 合意）。
> その代わり **⑦の AI レビューを必ず通す**。人間のチェックは事後に行われる。

---

## ① 調査（必ず最初にやる）

AI 分野は進化が速く、**手元の知識は古い前提**で動く。以下を毎回確認する。

| 調べること | 目的 | 検索の例 |
|---|---|---|
| 変換ライブラリの最新版・新顔 | 自前実装より良い選択肢が出ていないか | `markitdown docling marker` の最新リリース |
| Markdown 仕様・GFM の変更 | 出力書式が古びていないか | GFM spec の更新 |
| SDD / エージェント運用の知見 | このループ自体の改善 | spec-driven development の新手法 |

- 分かったことは **journal の「調査メモ」に 3 行以内**で書く（毎回長文を書かない）
- **方針を変えるほどの発見があった場合は、勝手に乗り換えず** `docs/feedback/INBOX.md` に
  「提案」として書き、承認を待つ

## ② フィードバックの取り込み

`docs/feedback/INBOX.md` を読む。未処理（`- [ ]`）の項目があれば：

1. 指摘を**仕様の変更**として解釈し、具体的な変更点に言い換える
2. 該当する要件 ID / タスク ID を特定する（無ければ新規に採番）
3. 処理したら `- [x]` にし、対応内容を 1 行追記する
4. **意味が取れない指摘は、勝手に解釈せず** journal に質問として書き、未処理のまま残す

> フィードバックは常に他のすべてのタスクより優先する。

## ③ 仕様の更新

実装より先に仕様を直す。**コードと仕様が食い違ったら、仕様が正**。

- `02-requirements.md` … 要件の追加・状態更新
- `05-conversion-rules.md` … 入出力の対応が変わったら必ず更新
- `01-product.md` … スコープや優先順位が変わったときだけ
- `04-tasks.md` … 新しいタスクの追加、優先度の並べ替え

**可読性チェック**（レビュー担当は非エンジニアの時間で読む前提）:
- 表で書けるものは表にする
- 1 文を 60 字程度までにする
- 「未対応」を隠さない。できないことほど目立たせる

## ④ 計画

`04-tasks.md` の上から **1〜3 件**選ぶ。選んだ根拠を journal に 1 行で書く。

やらないこと:
- 一度に多くのタスクを詰め込む（レビュー不能になる）
- 仕様が曖昧なまま実装する（→ 質問して次のタスクへ）

## ⑤ 実装（TDD）

1. 期待する入出力を**先にテストへ書く**（`tests/`）
2. 落ちることを確認する
3. 実装する
4. 通ることを確認する

規約:
- コメントと docstring は日本語。「何をしているか」ではなく**「なぜそうしたか」**を書く
- 公開 API を壊す変更は避ける。必要なら journal に明記
- 1 回のループで触るファイルは 3 つ程度まで

## ⑥ 検証

```bash
.venv/bin/pytest          # 全テスト
.venv/bin/ruff check .    # lint
.venv/bin/ruff format .   # 整形
```

**すべて緑でなければコミットしない。** 直せない失敗は、原因を journal に書いて
その変更を捨てる（壊れた状態を push しない）。

## ⑦ AI レビュー（人間のレビューの代わり。省略禁止）

成果物は人間の承認を待たずに `main` に入る。**ここが最後の関門**。

**実装した本人の文脈でレビューしても見落とす。** 必ず独立した視点を用意すること。

1. `/code-review` スキルが使えるならそれを実行する
2. 使えなければ、**サブエージェントに差分を渡してレビューさせる**
   （「この差分をレビューして。仕様 `docs/specs/` との整合、バグ、抜けたテストを指摘して」）

レビューの観点（この順に重い）:

| 観点 | 具体的に見ること |
|---|---|
| 仕様との一致 | 実装が `02-requirements.md` / `05-conversion-rules.md` の記述どおりか。**書いた仕様に嘘がないか** |
| 情報の欠落 | 変換で落ちる情報が、警告なしに黙って消えていないか |
| 出力の安定性 | 同じ入力で同じ出力になるか（辞書の順序、set の反復などに依存していないか） |
| テストの妥当性 | 実装に合わせてテストを緩めていないか。落ちるべきケースが落ちるか |
| 後方互換 | 公開 API（`convert_file` / CLI オプション）を黙って壊していないか |

指摘の扱い:

- **直せるものはその場で直す**（直した後にもう一度 ⑥ 検証を回す）
- 直さないと決めたものは、**理由つきで journal の「レビュー結果」に残す**
- 仕様の誤りが見つかったら、コードではなく**仕様を先に直す**

## ⑧ 記録とコミット

1. `docs/loop/journal/YYYY-MM-DD.md` を [テンプレート](#journal-のテンプレート)で作る
2. コミット（1 ループ 1 コミット、メッセージは日本語で要点）
3. `git push origin main`

**push 先は `main`。** PR は作らない（人間のレビューは事後に行われる）。
`main` が進んでいたら `git pull --rebase origin main` してから push する。

## journal のテンプレート

```markdown
# YYYY-MM-DD のループ

## 調査メモ
（最大 3 行。変化がなければ「特筆すべき変化なし」）

## 取り込んだフィードバック
- （なければ「なし」）

## やったこと
| タスク | 内容 | 変更ファイル |
|---|---|---|

## レビュー結果
（誰がレビューしたか／指摘と対応。直さなかった指摘は理由を明記。「指摘なし」でも書く）

## 👀 見てほしいところ
（レビューしてほしい箇所を具体的に。ここが一番重要）

## ❓ 判断を仰ぎたいこと
（仕様が決められなかった点。なければ「なし」）

## 積み残し
（次回に回したこと）

## 状態
テスト: XX 件すべて成功 ／ lint: 問題なし
```

## 中断・失敗したとき

| 状況 | どうするか |
|---|---|
| テストが直せない | 変更を捨てて journal に記録。次回に持ち越す |
| 時間切れ | できたところまでコミットし、積み残しを journal に書く |
| 仕様の判断がつかない | 実装せず「判断を仰ぎたいこと」に書く。**推測で進めない** |
| レビューで重大な指摘が出た | その場で直す。直しきれなければ**その変更は push しない**（journal には残す） |
| 3 回連続で同じタスクに失敗 | タスクを ❄️ 保留にし、理由を書く |

## この手順自体の見直し

**月に 1 回（毎月 1 日のループ）、この LOOP.md 自体を見直す。**
うまく回っていない工程があれば、その場で書き換えてよい（変更点は journal に記録）。
