# ドキュメントの地図

読む順番と、それぞれ「何が書いてあるか」の一覧です。
**仕様チェックのときは 📌 の 3 つだけ読めば全体が分かる**ようにしてあります。

## 仕様（`docs/specs/`）

| # | ドキュメント | 何が書いてあるか | レビュー優先度 |
|---|---|---|---|
| 01 | [プロダクト仕様](specs/01-product.md) | 何のためのツールか、誰が使うか、やらないこと | 📌 高 |
| 02 | [要件](specs/02-requirements.md) | 「〜できること」の一覧。実装状況つき | 📌 高 |
| 03 | [設計](specs/03-design.md) | 内部構造、なぜその作りにしたか | 中 |
| 04 | [タスク](specs/04-tasks.md) | やること一覧と優先順位。ループが毎晩ここから選ぶ | 中 |
| 05 | [変換ルール](specs/05-conversion-rules.md) | 入力がどんな Markdown になるかの実例集 | 📌 高 |

## 運用（`docs/loop/`, `docs/feedback/`）

| ドキュメント | 何が書いてあるか |
|---|---|
| [ループ手順書](loop/LOOP.md) | 毎晩 0 時に AI が実行する手順の定義 |
| [作業ログ](loop/journal/) | 各回の実行結果。「今日は何を変えたか」の記録 |
| [フィードバック](feedback/INBOX.md) | **あなた → AI**。仕様チェックの指摘を書き込む場所 |
| [AI からの質問](feedback/QUESTIONS.md) | **AI → あなた**。AI が決められなかった点。回答を書くと実装が進む |

## レビューの流れ

やり取りは **2 本の台帳**で行き来します。どちらもループが毎回必ず読みます。

```
   あなた ──── 指摘・要望 ────▶  feedback/INBOX.md     ──┐
                                                        │
   あなた ◀─── 判断が要る点 ───  feedback/QUESTIONS.md  ──┤──▶ 毎晩のループが
       └────── 回答を書く ─────▶                        ─┘     両方を最優先で処理
```

```
     あなた                              AI（毎晩 0:00 JST）
       │                                      │
       │  1. specs/ を読む                     │
       │  2. 気になる点を INBOX.md に書く       │
       │     QUESTIONS.md に回答を書く          │
       │                                      │
       │                          3. 2 本の台帳を最優先で処理
       │                          4. 仕様を直す → 実装 → テスト
       │                          5. AI が独立レビュー（人間の承認の代わり）
       │                          6. main に push し、journal に記録
       │                                      │
       │  7. journal を読んで次の指摘へ ────────┘
```

**成果物は事前承認なしに `main` へ入ります。**
その代わり、コミット前に AI が独立した視点でレビューし、結果を journal の
「レビュー結果」に残します。おかしければ後から指摘してください。

**回答が出るまで、AI はその論点に関わる実装を止めます。**
推測で作って手戻りするより、待つ方が安いからです。

指摘は書き方を気にせず、**「ここが分かりにくい」「これは違う」だけでも十分**です。
AI 側で仕様の該当箇所とタスクに変換します。
